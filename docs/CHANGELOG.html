1.3.0 — 2026-10-23

  • added No-sound hint — a file whose audio track nothing decodes used to play in silence with no explanation: the picture runs, nothing throws, and the track is simply never selected. Once the player is ready it now notices Tracks reporting audio groups with none selected, names the codec in a compact card, and offers Use FFmpeg, which switches the audio decoder live and remembers the codec. AudioSilence holds the rules — a silent film, or any selected track, is not a failure — so the hint stays away while the player is still preparing, when FFmpeg already is the choice, and after it is dismissed for that video. 11 JVM tests pin those cases (83 in total)
  • added Remembered audio fixes — the no-sound card's FFmpeg button records the codec it rescued (AC3, DTS, …); the next file with that codec switches to FFmpeg by itself when nothing decodes it, no card and no tap, while the saved decoder priority is left alone. Settings → Playback lists them and can forget them, and the automatic switch's own message carries a Forget action, so a codec that turns out to be a one-off can stop switching without leaving the player
  • added Audio-only rescue — the no-sound card and the automatic switch move just the audio decoder, through a session command of their own (PlaybackCommands.setAudioDecoder); a file whose sound needs FFmpeg keeps hardware video decoding, and the saved decoder priority is untouched, while the stream panel's chips still change both halves because there the viewer chooses on purpose
  • added Remembered codecs switch before the first frame — a codec you already rescued used to cost a silent moment per video: the player had to be ready and the audio track already missing before the switch could be applied. The player now reads the file's own audio track before playback starts and, when that codec is remembered, picks the FFmpeg audio renderer at prepare time, so the sound starts with the picture. The read goes through Media3's own extractors — the parser that will play the file — because the platform MediaExtractor does not list every track: handed the AC-3 clip, it reported one video track and no audio, which would have made the pre-switch give up on exactly the codec it exists for. The early and the live path share one decision and one spelling of the codec name (audio/ac3 → AC3), which AudioCodecProbeTest pins; a file the probe cannot read and a track remembered under its label keep the live switch, which is still there. 5 more JVM tests (92 in total)
  • added The probe is remembered per file — the early switch read the header again on every play, including files this session had already answered for. The codec a probe finds is now kept in AudioCodecCache under the file's own identity (its size and the moment MediaStore added it, both already on the item), so a file opened a second time costs no header read at all. A re-downloaded or edited file lands on a new key and is probed again rather than inheriting an old codec, an item whose size is still unknown gets no key, and only findings are stored — a file that could not be read gets another chance. The map is bounded and least-recently-used, so a long session cannot grow it. 5 more JVM tests (97 in total)
  • added The cache hit is measured, not argued — the promise is that a file already probed is never opened again, and a container read gives no way to see an open from outside. AudioCodecProbe.probe now takes the track read as a parameter and the cache rule lives in AudioCodecProbe.resolve, so the JVM tests pass a read that counts: the second play must not open the file, a changed key and a failed read must, and a file with no audio is never remembered. Production still opens the file with Media3's extractors, and AudioCodecProbeDeviceTest repeats the same counts on the emulator against the packaged ac3.mkv, where the real read also has to name its track AC3. 5 more JVM tests (102 in total)
  • added Probe results survive a restart — the cache lived in the heap, so the first play after every launch paid for the header read and started the picture a moment before the sound. What a probe finds is now written down (PrefsAudioCodecStore, one tab-separated line per entry in SharedPreferences) and read back when the next run opens its first file. The key already carries the size and the timestamp that change when the bytes do, so a re-downloaded or edited file is still probed again; the written map is the same bounded LRU map the memory keeps, so the file cannot grow past eight entries, and a hit — the common case — writes nothing at all. A line that does not name both a key and a MIME type is dropped rather than guessed at. 8 more JVM tests (110 in total)
  • added Auto-advance switches too — an episode reached by the player itself fell back to the live rescue: the next file started silent and the switch only arrived once the picture was already running. The player now reads the codec of the item after the current one while the current one plays, and on arrival applies the same audio-only switch to the new item, with the same message and Forget action. The read costs one header read per arrival, and none for a file this process already answered for. One switch covers the rest of the queue — the audio decoder belongs to the session — so a season does not announce the same codec every episode; choosing a decoder in the stream panel clears that, because the viewer has just changed what the session does. A queue played from the start still gets the switch before the first item is prepared
  • added The stream panel's audio line says not decoded instead of “waiting for tracks” when there is an audio track that nothing is playing
  • added Device-level coverage for both: the emulator job asks the silent-audio premise of a real player (ac3.mkv under “hardware only” must report an undecoded AC-3 track, the FFmpeg run none, and the audio-only rescue must take that clip to decoded audio while the video decoder mode is exactly what it was before the switch, while a fourth AC-3 test picks the audio decoder before the item is prepared and finds it already decoded at the first ready state), and a Compose test renders the player's snackbar host and checks that an announcement appears above the control bar
  • added The silence is announced before it starts — the no-sound card could only report a file that was already playing quietly. The header read that picks the decoder now also answers whether anything on this device can decode the track at all: AudioPreflight asks the platform's own codec list and NextLib's FFmpeg build, and a codec neither names gets a card that says so before the file is opened, with no FFmpeg button — switching would be a promise the codec cannot keep. The same check covers a queue from its first item and every episode the player reaches by itself, and it deliberately says nothing when a list cannot be read, when the file has no audio, or about a codec name left by an older cache. The value the probe remembers is now the file's audio MIME types, since that is the only form either question can be asked of — and every track, because one playable track is sound; entries holding a bare codec name are dropped and read again. 11 more JVM tests (121 in total)
  • added Device coverage for the new lists: on the emulator, ac3.mkv's audio must come back as audio/ac3 and be judged playable, while a codec nothing ships must be reported as undecodable rather than passed over
  • added The warning is also a way out — a file no decoder here can read used to end there: the card said why the picture was quiet and offered nothing, because the decoder switch it could offer would not keep its promise. When the queue holds another video the card now also carries Next video, which skips over a file that can only ever be silent; a one-item queue, or repeat-one, keeps the card alone, since skipping would only restart the same file
  • added The recall is measured on a device too — aRecallNeverOpensTheFile asks for a file nobody probed and finds nothing with zero opens, then probes it once and finds the answer with that same single open, which is the whole claim the library badge makes
  • added The library says it before you open the file — for the whole library — the no-sound warning only arrived with the file already open, and a library badge could only mark a file the player had opened, while it was still among the eight entries the probe cache keeps. Both halves are fixed. A file whose audio nothing here can decode now carries a muted-speaker badge on the thumbnail in grid view, an icon beside the title in list view, and an Audio row in the details dialog that spells it out — and the mark reaches files nobody has played. Drawing a row still opens nothing, and a decision is now its own record: AudioVerdictIndex keeps one bit per file under the probe's key (512 of them, least recently used out first) in a SharedPreferences file of its own, so a badge survives both a restart and the cache evicting the file. AudioVerdictSweep fills in the rest: on the library screen it walks the files nobody has decided, off the main thread, reading a header only for a file that needs one and stopping after 120 undecided files a visit, so a huge — or partly cloud-backed — library cannot become one long silent read; badges appear over a few visits instead. The sweep also leaves the player's probe cache alone, and nothing uncertain is written: a read that failed, an unreadable decoder list or an old codec name is left undecided and retried, while a file with no audio track is settled so it is not re-read every visit. The mark and the player's card stay one rule (AudioVerdictSweep.decide over AudioPreflight.outlook). 22 more JVM tests (145 in total), and the emulator job round-trips the new verdict file through a second instance
  • added The library can be read as folder sections — a flat grid answers “what is new” but not “what is in the Camera folder”: the chips could narrow the list to one folder and nothing could show them all at once. A folder button in the toolbar (and the same switch in Settings → Appearance) now draws the library as sections, in folder-name order, with the chosen sort still ordering the files inside each one and a count on every heading. Each heading is also the shortcut to its folder filter, toggling the chip that was already there, and it stays pinned to the top of the list while its own files scroll underneath it — giving way only when the next folder's heading arrives — so a long section never leaves its tiles unnamed. A play button on the heading starts that folder from its first file and queues that folder alone, so the section ends where it ends instead of rolling on into the next one. Grouping is a layout, not a filter: search and the chips still apply first, next/previous walk what is on screen — folder by folder — and the setting survives a restart like the grid columns and sort order. The rules live in LibrarySections, so the order a section promises is pinned by LibrarySectionsTest (4 more JVM tests, 149 in total) rather than argued from the screen, and what a section is actually drawn as — a heading that names its folder, carries its count, spans the row in grid mode and toggles the filter when tapped — is covered by LibraryFolderSectionsTest on the emulator, including that the heading is still on screen once its first files have scrolled away, that the next folder's heading takes its place at the top, and that the play button hands the player that folder — in drawn order, from its first file — rather than the whole library
  • fixed Announcements made in the player were invisible: it is a full-screen overlay outside the Scaffold, so the app's SnackbarHost was never composed while a video was open and every message (decoder switch, repeat mode) queued forever. The player now carries its own host above the control bar, and higher while the stream panel is open

1.2.0 — 2026-10-16

  • added Live decoder switching — the player's stream panel switches between hardware and FFmpeg decoding while the video keeps playing, through NextLib's DecoderManager attached to the one ExoPlayer; the UI asks the service over a custom Media3 session command and the service applies it on the player's thread and remembers it
  • added Audio track picker — the control row lists every audio track of the current file (codec, channels, language) and switches between them through TrackSelectionParameters; TrackOptions builds the list so the indices handed back are the ones the player reported
  • added Subtitle auto-discovery — a .srt / .vtt / .ass file with the video's own name (or a language tag such as Movie.th.srt) loads by itself: exact name first, then the device language, then the rest, and files of other videos never match
  • added A new SUBTITLE log tag that records every subtitle search, including the ones that find nothing
  • added 18 more JVM tests (72 in total): subtitle name rules, the decoder preference table, audio track options built from real Media3 Tracks objects, and the promise that a stopped receiver has really let go of the port
  • changed Hardware only now means hardware MediaCodec decoders only; the FFmpeg renderers stay built in every mode, because the renderer set is fixed when the player is created — that is what makes switching to FFmpeg mid-video possible
  • changed Subtitle auto-discovery reads MediaStore, so on Android 13 and newer it only sees subtitle files this app owns; the subtitle button still takes any file you pick
  • fixed Stopping a receive session now really closes the port: on Linux a thread parked in accept() kept the closed socket alive, so the receiver could take one more file after the screen said it had stopped

1.1.0 — 2026-10-16

  • added Wi-Fi transfer (`Transfer` tab) — send files from one phone to another on the same network: no cable, no cloud, no account
  • added Receive mode runs a small HTTP server, shows the address and a four digit code, and advertises over mDNS so the other phone finds it without typing
  • added Send mode lists discovered receivers or takes a typed address (192.168.1.20, 192.168.1.20:45871, http://…), with a Check button before you pick files
  • added Several files per transfer with progress, cancel and per-file outcomes; a cancelled or interrupted transfer leaves no partial file behind, and the receiver stays usable
  • added Received videos are published to Movies/VDO Player through MediaStore IS_PENDING and appear in the library at once; other files go to Download/VDO Player
  • added Files whose size a provider does not report are streamed with a chunked request body — the sender never holds the whole file in memory
  • added New TRANSFER log tag records every incoming and outgoing file with its size and the peer address
  • added ACCESS_LOCAL_NETWORK and its runtime prompt for Android 17, which blocks local network traffic — mDNS included — for apps targeting SDK 37
  • added Wi-Fi Direct for phones with no router between them: the receiving phone opens a group, the sender joins it, and the group owner appears in the normal receiver list. Asks for NEARBY_WIFI_DEVICES (13+) or ACCESS_FINE_LOCATION (≤12) when first used
  • added Repeat in the player's control row: off → the whole queue → this video, announced on screen and remembered for the next session
  • added Seek preview: dragging the progress bar or scrubbing with a swipe decodes a frame of the target position into the heads-up display, cached per two-second bucket and switchable in Settings
  • added 54 JVM unit tests over the wire protocol, the file-name sanitiser, the chunked path, cancellation, the repeat cycle, the seek-preview policy, the Wi-Fi Direct address rules and translation completeness; CI runs them before building a release
  • added GitHub Actions release workflow (.github/workflows/release.yml): a v* tag runs the tests, builds the four APKs, signs them from repository secrets and opens a draft release with the SHA-256 checksums in the run summary
  • changed The manifest now declares INTERNET and ACCESS_NETWORK_STATE for the transfer sockets. Nothing is uploaded to the internet; files only move between two phones on your own network
  • fixed File names keep Thai vowel marks and ordinary punctuation — only what a file system cannot take becomes _
  • fixed Long file names are shortened without losing the extension, so a long video still lands in Movies
  • fixed Cancelling an upload says “Cancelled” instead of an internal I/O error, and a sender walking away is no longer logged as an app failure
  • fixed The transfer screen resolves its probe wording at composition time, so a language change while it is open cannot leave a stale message behind

1.0.0 — 2026-10-15

First public release. Everything below is new.

Library

  • added MediaStore scan with a ContentObserver, so the list updates while the app is open
  • added Thumbnails decoded from the video frames themselves (Coil 3 + coil-video)
  • added Search by title or folder, folder filter chips, seven sort orders
  • added Grid layout with 1–4 columns and a single-column list layout
  • added Long-press details: folder, resolution, duration, size, MIME type, relative path, URI

Playback

  • added ExoPlayer hosted in a MediaSessionService, driven through a MediaController
  • added FFmpeg software decoders via nextlib-media3ext, three priority modes
  • added Playlists from the filtered library view with previous/next
  • added Per-video resume positions, throttled to one write every 5 seconds
  • added Background audio with a media notification that returns to the player
  • added 0.25×–3× speed, plus a 3× long-press boost
  • added Aspect modes, control lock, rotation, picture-in-picture with the real aspect ratio
  • added Side-loading of .srt, .vtt and .ass subtitles, and a subtitle toggle
  • added Gesture layer: brightness, volume, scrub, double-tap seek, all with on-screen feedback

Diagnostics

  • added LogBus — 2000-entry ring buffer, versioned snapshots, logcat mirroring, 8 tags, 6 levels
  • added LogFileWriter — asynchronous rotating files, 2 MB × 10
  • added CrashGuard — uncaught exceptions logged with a device summary and flushed before exit
  • added Diagnostics — device, OS, ABI, display, memory, storage, player state, active tracks, MediaCodec inventory
  • added LogShare — .txt/.zip exports, share sheet delivery, save to Downloads
  • added Logs screen: level/tag/text filters, freeze the live tail, copy, clear, share, save

App

  • added Material 3 with dynamic colour, light/dark/system themes
  • added Settings for appearance, playback and diagnostics
  • added Recent tab with per-entry progress, remove and clear-all
  • added Handles ACTION_VIEW and ACTION_SEND for video/* and audio/*
  • added Adaptive launcher icon with a monochrome variant for themed icons

Distribution

  • added Per-ABI release APKs plus a universal APK, signed with the project key
  • added This GitHub Pages site, resolving the newest release through the GitHub API
  • added Markdown and HTML documentation

Known limitations

  • limit No device-level smoke test ran: playback correctness is asserted from API contracts and build artefacts, not a recorded device run
  • limit Documentation screenshots are vector mockups of the shipped layouts
  • limit Minification is disabled for release builds, so APKs are larger than necessary
  • limit Some Player commands are not available to a MediaController; refusals are logged and automatic selection is kept
  • limit Before Android 10, exports are saved to the app's private external directory (the public Downloads path needs a runtime storage permission there)

Security

  • added Release keystore and keystore.properties are excluded from version control; releases are signed locally
  • added The app requests no INTERNET permission
