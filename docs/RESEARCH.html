The decisions behind the build, the versions that were verified against Google Maven and Maven Central, and the numbers measured on the build machine.

Full text: docs/RESEARCH.md

1 · Decoder strategy

Phones ship hardware decoders for mainstream formats only. The failures users actually hit:

  • MKV with AC-3/DTS audio → video with no sound
  • VP9/AV1 on chips that predate them → refuses to start
  • HEVC 10-bit and odd profiles on older SoCs → decoding error

Three options were evaluated for a Media3 app.

OptionWhat it offersVerdict
Official Media3 FFmpeg extension Not published to Google Maven. You check out Media3, build FFmpeg with the NDK and depend on the module locally; it provides an audio renderer. Rejected — would vendor a native toolchain into this repository.
NextLib io.github.anilbeesetti:nextlib-media3ext Drop-in RenderersFactory with FFmpeg + dav1d video decoders. Video: H.264, HEVC, VP8, VP9, AV1. Audio: Vorbis, Opus, FLAC, ALAC, PCM, MP3, AMR, AAC, AC-3, E-AC-3, DCA, MLP, TrueHD. ABIs: armeabi-v7a, arm64-v8a, x86, x86_64. Chosen — two lines to integrate, matched to Media3 1.11.1, published to Maven Central. Licence GPL-3.0. Its DecoderManager (from 1.11.0-0.14.0, included in the pin) switches between hardware, software and FFmpeg decoders while a video keeps playing, which is what the player's decoder chips use.
LibVLC org.videolan.android:libvlc-all:3.7.7 Separate engine with the broadest coverage, HDR and passthrough support. Rejected for 1.0.0 — rewrites playback and UI bindings, adds another large native payload. Kept as the fallback plan.

The chosen renderer priority is exposed to the user: Hardware first (EXTENSION_RENDERER_MODE_ON, the default), Prefer FFmpeg (…_PREFER), Hardware only (…_OFF). Hardware decoding is kept in front because it uses less power; FFmpeg only takes over what the platform cannot handle.

3 · Build system: AGP 9 and built-in Kotlin

AGP 9 ships built-in Kotlin support. Applying org.jetbrains.kotlin.android now fails outright, and android { kotlinOptions { … } } is replaced by kotlin { compilerOptions { … } } — which is where the Media3 -opt-in=…UnstableApi flag lives. The Compose compiler plugin (org.jetbrains.kotlin.plugin.compose) is still required and must match the pinned Kotlin version.

4 · Playback architecture

  • PlaybackService : MediaSessionService owns the single ExoPlayer, which is what makes background audio, the media notification and media-button handling work.
  • The UI uses a MediaController and pulls state on a 500 ms ticker plus player events — one code path, no callbacks against a released player.
  • Track steering goes through TrackSelectionParameters; commands the session refuses are caught, logged and ignored rather than crashing playback.
  • The decoder preference is mirrored into SharedPreferences because a MediaSessionService cannot read DataStore synchronously at startup.

5 · Packaging and measured size

Artefact1.0.0–1.3.0 (unminified)1.4.0 (R8)
app-arm64-v8a-release.apk24 MB11 MB
app-armeabi-v7a-release.apk23 MB10 MB
app-x86_64-release.apk28 MB14 MB
app-universal-release.apk51 MB37 MB

Native libraries inside the APK include libavcodec.so (5.6 MB for arm64), libavutil.so, libswscale.so, libswresample.so and libmedia3ext.so per ABI. That is why ABI splits are enabled with a universal APK kept as a safety net.

Minification was deliberately off for 1.0.0–1.3.0: no device participated in verification, so the predictable build won over a smaller one. It is on from 1.4.0, because the measurement said the caution was buying less than it cost: the four dex files unpacked to 52 MB inside a 24 MB APK, and the keep rules had grown into -keep class androidx.media3.** plus -keep class com.nardech.vdoplayer.**, which kept the whole app and left the shrinker almost nothing to remove. The rules now name only what is reached by name — NextLib's JNI classes, every native method's name, and the class names the log screen prints — while Media3's own consumer rules cover the renderer constructors it loads reflectively. The dex went from 52 MB unpacked to 4.75 MB.

7 · Why the screenshots are vector mockups

No Android device or emulator took part in building this release, so the documentation shows mockups that reproduce the shipped layouts instead of claiming to be device captures. The emulator cannot start on the build machine: CPU virtualisation is disabled in the firmware (Virtualization Enabled In Firmware: No), so Google's Android Emulator hypervisor driver installs but never loads and the emulator exits with x86_64 emulation currently requires hardware acceleration!.

What is verified without a device: 40 JVM tests stand up the real receiving server on a loopback socket and drive it with the real client — upload, wrong code, missing length, truncated body, chunked body, three concurrent uploads, code rotation, hostile file names and cancellation — lint reports no errors, and aapt2 dump resources lists the (th) values that were packaged. That is evidence about the protocol and the resources, not about pixels or MediaStore on a real phone.

9 · Wi-Fi transfer: why HTTP on the LAN

DecisionReason
Plain HTTP/1.1 on a socket, written by handNo dependency, no Play Services, no native code. One Kotlin file holds the protocol, and the whole wire contract is covered by JVM tests over loopback sockets
A four digit code in a headerThe receiver cannot tell a friendly phone from a hostile one on a shared network; the code is the only authorisation, and it rotates on demand and after repeated wrong attempts
mDNS (NsdManager) discovery with a typed address as fallbackCaptive portals and guest networks that isolate clients break multicast; the manual path keeps transfers working there
MediaStore IS_PENDING on Android 10+A half-finished transfer is invisible to the gallery; only commit() publishes the file
Files land in Movies/VDO PlayerThe app's own MediaStore scan shows the new video without a restart

Permissions this needs on modern Android

UseAndroid 12 and belowAndroid 13–16Android 17, targetSdk 37
ServerSocket listening on the LANINTERNETINTERNETINTERNET + runtime ACCESS_LOCAL_NETWORK
NsdManager register / discoverINTERNETINTERNET — NSD is not one of the Wi-Fi APIs NEARBY_WIFI_DEVICES coversINTERNET + ACCESS_LOCAL_NETWORK
Wi-Fi Direct (WifiP2pManager) — not used hereACCESS_FINE_LOCATIONNEARBY_WIFI_DEVICESNEARBY_WIFI_DEVICES (+ ACCESS_LOCAL_NETWORK for the traffic)

Android 17 enforces the Local Network Protections project for apps targeting SDK 37: an incoming TCP connection, an outgoing connection to a local address and mDNS all need ACCESS_LOCAL_NETWORK (part of the Nearby devices group). Without it the traffic is blocked by the network stack, and a blocked TCP connection looks like a timeout rather than a permission error — which is why the app asks before starting a receive session and explains itself when the permission is missing. Apps targeting SDK 36 or lower keep an implicit grant through INTERNET, so the requirement only appeared when the target SDK moved to 37.
